# Lessons — Kopi Studio 2a handoff

**Last Updated**: 2026-07-27 SGT

## 2026-07-25 — `[color:var(--token)]` only works for the raw-value half of the token set
**What happened**: Repainting the overlay primitives, `text-[color:var(--card)]` was written for a cream glyph. It renders no colour at all.
**Root cause**: `src/index.css` holds two token families. The shadcn compat layer (`--card`, `--primary`, `--secondary`, `--border`, `--ring`, `--popover`, `--foreground`, `--sidebar-*`) stores bare **HSL triples** — `--card: 40 55% 96%` — which are only valid inside `hsl(var(--…))` or via the Tailwind semantic class (`bg-card`). The 2a layer (`--fg`, `--fg-dim`, `--row-hover`, `--row-selected`, `--cta-primary-*`, `--brown-text`, `--red-soft`, `--surface`, `--delta-*`, `--status-*`, `--drawer-overlay`) stores complete colour values and is the only half usable in an arbitrary `[color:var(--…)]` utility.
**Fix**: Use the semantic class for the shadcn half (`bg-card`, `text-foreground`, `border-border`) and `[color:var(--…)]` for the 2a half. `--surface` `#faf6ee` is the raw-value twin of `--card` when an arbitrary value is genuinely needed.

## 2026-07-25 — A flat tint is not a focus indicator on cream
**What happened**: `DropdownMenuItem`, `SelectMenuItem` and the `SearchableMultiSelect` option list all marked keyboard position with `bg-secondary` alone.
**Root cause**: `--secondary` `#F3EDE3` against the cream menu surface `#FAF6EE` measures 1.08:1 (1.16:1 on raised white). It was inherited from the navy era, where the same class was a light wash on a dark panel and therefore obvious.
**Fix**: Focus takes an inset brown ring (`focus-visible:ring-2 focus-visible:ring-inset focus-visible:ring-ring`) plus the deeper `--row-selected` (brown 12%) fill, and hover drops to `--row-hover` (brown 6%) so the two states stay distinguishable. Any tint-only state carried over from the dark theme needs re-measuring, not just re-colouring.

## 2026-07-25 — The header's "Search records" button dispatched an event nobody listened for
**What happened**: Retiring the desktop masthead looked like it would cost the app its universal-search entry point. It cost nothing: both the desktop ⌘/ pill and the mobile search button fired `window.dispatchEvent(new Event('open-global-search'))`, and a repo-wide grep found **zero** `addEventListener('open-global-search')`. The button had never done anything.
**Root cause**: The affordance was built ahead of the search surface it was meant to open. `GlobalCommandPalette` — the only palette that exists — listens for `open-command-palette` (plus ⌘K).
**Fix**: `AppHeaderMobileBar`'s button now dispatches `open-command-palette`, which makes it the only touch route to module navigation below `lg` (⌘K has no touch equivalent, and the rail is hidden there). Before deleting chrome, grep for the *listener*, not just the dispatcher — a wired-looking control can be inert, and an inert one can be repointed at something real instead of rebuilt.

## 2026-07-25 — "The only X in the app" was asserted, not scanned — and it was wrong
**What happened**: The PRD justified removing the intake 🎯 by calling it *"the only saturated off-palette mark in the app."* The profiler's own result screens carried four more emoji (`ResultHero` `{p.em}`, `PlaybookSection`'s five `catIcons`, `ScoreCard`'s 👔, `ResultSections`' ⚠) plus four DISC hex tints. Three screens of one wizard were purged and its result was left on the old rule, so the flow changed design language between step 7 and step 8.
**Root cause**: The claim was written from the screen in front of the author. A repo-wide scan takes one command — `LC_ALL=C grep -rnoP '[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]' src/` — and was never run.
**Fix**: Before writing a uniqueness claim ("the only", "the last", "nothing else") into a PRD or a decision, run the grep that would falsify it and paste the result. When a rule is applied to part of a flow, the unit of work is the FLOW — `ResultHero`/`PlaybookSection`/`ScoreCard`/`ResultSections` are reached from the same wizard and are also reused by `StoredResultReport`, so a half-applied rule shipped to two surfaces at once.

## 2026-07-25 — The list skeleton painted itself in a colour that does not exist on cream
**What happened**: All three P5 lists (Clients, Results, ManageAccounts) open in `variant="loading"`, so the first thing a user saw was six blank hairline-ruled rows. The skeleton blocks were rendering — in a colour nobody could see.
**Root cause**: `DataTableLoadingBody` filled its blocks with `bg-secondary` `#F3EDE3`: 1.06:1 against the page cream and 1.08:1 against card cream, then dimmed further by a per-column `opacity: 0.9 - j * 0.1` ramp. `index.css` already ships the pair `--skeleton` `#E0D3C3` (the block) and `--skeleton-hi` `#F3EDE3` (the highlight sweep); the file had reached for the highlight end as the fill. `LoadingSkeleton.tsx` used `--skeleton` correctly all along — this one file was the outlier.
**Fix**: Blocks paint `bg-[color:var(--skeleton)]`. Separately, the skeleton row always drew a 16px checkbox placeholder even though all three lists pass `selectable={false}`, so the placeholder was a column wider than the table it stood in for — `selectable` is now threaded through `DataTableLoadingBody` from `DataTable`. When a token pair reads `--x` / `--x-hi`, confirm which half is the fill before using either.

## 2026-07-25 — A printed financial timestamp was browser-local on a helper named for Singapore
**What happened**: The portfolio PDF's "Generated: …" stamp, the client report's "as of" date and the disclaimer's "Report generated:" line were all wrong by hours — or by a day west of SGT — on any non-SGT machine.
**Root cause**: `getCurrentSingaporeTime()` returns a bare `new Date()`. The instant is right, but the NAME promises a zone the value does not carry: every getter and every `toLocaleString`/`toLocaleDateString` without an explicit `timeZone` reads the browser's zone. This exact trap was already written up in `src/features/crm/lib/lessons.md` (2026-07-14), which even named these callsites as unfixed — the note was logged but never actioned.
**Fix**: The three display strings route through `formatDisplayDateTimeLong` / `formatDisplayDateLong`, which pin `timeZone: SINGAPORE_TIMEZONE`. `finance.ts`'s `currentRefYear()` — which drove the CPF retirement-sum lookup a year early west of SGT — now calls a new `getSingaporeYear()` in `timezoneUtils`, and `getCurrentSingaporeTime()`'s own docblock now warns what it does and does not guarantee. The finance golden test was asserting `currentRefYear() === getCurrentSingaporeTime().getFullYear()`, i.e. agreeing with the bug on every machine except during the SGT new-year window; it now asserts against `getSingaporeYear()`. An audit note in a lessons file is not a fix — if it names callsites, someone has to go to them.

## 2026-07-25 — A hex grep scoped the repaint at 5 files; the real surface was 103
**What happened**: The palette inversion was scoped from a grep for the retired navy/gold **hex literals**, which returned 5 files. The repaint actually ran to **103 files / 158 findings** over four adversarial rounds (158 → 76 → 23 → 1) — see the P1 row in [KOPI_STUDIO_REDESIGN_PRD.md](../../active/KOPI_STUDIO_REDESIGN_PRD.md).
**Root cause**: A colour is a *rendered value*, not a string, and the retired palette reached the screen in at least five forms a hex grep cannot see. (a) `rgb()` / `rgba()` triples. (b) Tailwind 4 arbitrary values, whose channels are **space-separated** — `bg-[rgb(201_168_76_/_0.14)]` is gold, and it matches neither a hex grep nor an `rgb(r, g, b)` grep. (c) Cool-neutral utility classes: `zinc-*` / `slate-*` / `gray-*` read as "grey" but are blue-biased and only look correct against navy. (d) Semantic tokens whose *class names* are innocent (`bg-card`, `bg-sidebar`) while their **values** in `src/index.css` were navy. (e) Type had the same shape — the stack was declared inline as `style={{ fontFamily: … }}` inside components rather than only in the token layer.
**Fix**: Enumerate the colour *space* before scoping. Resolve every retired value in the token layer first, then grep once per rendering form of each value — hex, `rgb(`, the underscore-separated arbitrary form (`grep -rn "201_168_76" src/`), the cool-neutral class families, and `fontFamily`/`font-\[` for type. Both sweeps are now clean: `grep -rEo '\b(bg|text|border)-(zinc|slate|gray)-[0-9]+' src/ --include=*.tsx` returns **0**, and every surviving inline `fontFamily` reads `var(--font-sans|pixel|mono)`. A scoping grep that returns a suspiciously small number is a signal the grep is wrong, not that the job is small.

## 2026-07-25 — A `paths:`-scoped rule file is executable policy, and it outlived the palette it described
**What happened**: `.claude/rules/dark-mode.md` carried `paths:` frontmatter matching `src/**/*.ts(x)`, so it auto-loaded into **every agent that touched a source file** and asserted the app was permanently navy/gold and always dark. Left in place it would have instructed every later phase to revert the migration it was running inside — an agent would read "the cardinal rule: cards are one step LIGHTER than the near-black page" as current law while repainting onto cream.
**Root cause**: Rule files under `.claude/rules/` are not documentation. They are injected context with the same force as `CLAUDE.md`, and nothing about editing `src/index.css` makes an agent look at `.claude/rules/` first. The rule described a *fundamental* (the theme's polarity), which is exactly the class of fact a migration invalidates wholesale.
**Fix**: Replaced by [`.claude/rules/light-theme.md`](../../../../.claude/rules/light-theme.md) — same `paths:` scope, inverted surface contract, debugging-history sections preserved verbatim. **When a migration changes a fundamental, audit `.claude/rules/` BEFORE touching code**: `grep -l "paths:" .claude/rules/*.md` gives you every file that will be read aloud to every subsequent agent. Rewriting the rule is part of phase 1, not part of the docs pass at the end.

## 2026-07-25 — Translucency reverses direction when you invert a theme
**What happened**: Constructions that had *darkened* on navy began *lightening* on cream, silently inverting contrast. Two shapes carried it: a translucent cream wash used as a "recess" inside the client-facing PDF's brown hero, which composited **up** to `#9D8062` and dropped the inherited cream type to **3.42:1** on the printed artifact; and `hover:bg-primary/90` on the brown primary CTAs, where hovering made the fill *lighter* — the opposite of the affordance.
**Root cause**: An opacity modifier composites toward whatever is behind it. On a dark ground "translucent light ink" reads as a darker step because the surround is darker still; on a light ground the same declaration reads as a wash toward white. The declaration is unchanged, the direction is not — so a class-for-class palette swap preserves the bug and hides it, because the code looks identical and only the composite moved.
**Fix**: A recess on a dark fill must be **ink-based**, not light-based: `.report-stat` in `src/features/crm/lib/report-print.css` now paints `rgb(58 46 36 / 0.1)` (Kopi ink at 10%, compositing to `#836444`), restoring every line to 5.03:1, and the comment above it records both measurements. CTA hover/active moved from an alpha modifier to the explicit darker steps `--cta-primary-bg-hover` `#7d5f3d` / `--cta-primary-bg-active` `#6d5233`; `grep -rn "hover:bg-primary/90" src/` is now **0**, and `SendEmailDialog.tsx:158` + `LineItemsEditor/index.tsx:129` carry in-file notes so it is not reintroduced. **Still open**: the same construction survives on the destructive variant — `hover:bg-destructive/90` at `src/components/ui/button.tsx:15` and `src/components/primitives/shell/Button.tsx:92`, over `--destructive` `#AB4925` — and needs the same measurement.

## 2026-07-25 — Removing a card wrapper moves the text onto a different ground
**What happened**: The list archetype dropped its card in favour of hairline rows. The row markup was untouched, but its meta text went from sitting on card cream to sitting on the page cream — `--fg-muted` `#7d6b5b` measures **4.72:1 on card cream `#faf6ee` and 4.12:1 on page cream `#f0e6d6`**. A layout change with no colour edit shipped an AA failure.
**Root cause**: Contrast is a property of the *pair*, and half the pair is contributed by an ancestor. The three-step light ladder (page → card → raised) is only ~0.15 in ratio per step, which is enough to cross 4.5:1 without being visible in review. The same trap applies in reverse: `--row-hover`, a 6% brown wash tuned against card cream, is effectively invisible against the page.
**Fix**: Bare-surface meta carries its step by **size**, not by a lighter ink — 12px `--fg-dim` `#5d4f3f` instead of `--fg-muted` (see the decisions entries "The list table loses its card" and "`AppSidebar` rail ships on card cream"). Generalise it: whenever a wrapper is deleted, added, or the surface under a component changes, re-measure every text token in the subtree against the *new* ground before shipping. `--fg-muted` is the canary — it is the only ink token that is AA-safe on one surface and not the other.

## 2026-07-25 — A comment that certifies its own compliance is a defect when it is wrong
**What happened**: Several files carried comments asserting they were already compliant — flat claims of the form "every line keeps its 4.58:1" — while the surfaces they described were failing. The comments were repeatedly the thing that misled the auditors: an agent reading a stated, specific ratio treats the question as settled and moves on, so a lying comment costs more than no comment at all.
**Root cause**: The claims were written when they were true of the surface in front of the author, then survived a change of ground (see the two lessons above) with no re-measurement. Precision reads as evidence — "4.58:1" looks measured whether or not anyone measured it.
**Fix**: A contrast claim in a comment must name **which type on which surface**, so the claim falsifies itself when the surface moves. The corrected note above `.report-hero-sub` in `src/features/crm/lib/report-print.css` is the model — *"every line sitting **DIRECTLY** on the brown keeps its 4.58:1. Type inside `.report-stat` sits on that rule's ink recess instead and measures 5.03:1"* — scoped, with the exception named and its own figure. Comments recording an AA budget are load-bearing: `src/index.css` and `ResultHero`'s docblock now carry the measured floors precisely so the next pass does not re-derive them, which only works if they are true.

## 2026-07-25 — Two components that must be complementary declared their breakpoints independently
**What happened**: `AppHeaderMobileBar` was `md:hidden` while the desktop rail rendered at `hidden lg:flex`. Between **768px and 1023px** the bar had hidden itself and the rail had not yet appeared, so the viewport had **no navigation at all** — a pre-existing bug, unrelated to the redesign, found only because the rail work forced both files open at once.
**Root cause**: The pair is a mutually exclusive switch, but each half owned its own literal and neither referenced the other. `md` and `lg` are both plausible in isolation; only the pair is wrong, and nothing type-checks a pair of Tailwind variants.
**Fix**: The bar moved to `lg:hidden` (`AppHeaderMobileBar.tsx:82`), matching the rail's `lg` mount, with the reason recorded in its own docblock at line 11. When two components partition a range, the breakpoint belongs to *one* of them and the other must cite it — the rail exports `SIDEBAR_OFFSET_CLASS` for exactly this reason. Check the pair by resizing to the widths *between* the two named breakpoints, which is the only band where the bug exists.

## 2026-07-27 — A ratio booked at exactly 4.50 was a rounded 4.499, and axe fails it
**What happened**: The report surfaces threw a `serious` axe `color-contrast` violation on five nodes at once — the three `report-health-card-*` band labels (12px), and both `.report-row-loss .num` opportunity-cost cells (13px) — plus the `danger` `PageShellStatusPill` on the profiler result detail. Every one was `--negative-text` `#AB4925` on the error tint `#FAE0D6`, the single pairing the 2a handoff had booked as "4.50 ✅".
**Root cause**: The pairing measures **4.4995**. It was written down as `4.50` and then treated as passing everywhere it was quoted — `KOPI_2A_SPEC.md`, `COLORS.md`, `financeReportBands.ts`, `report-print.css`, the 2a `decisions.md`. WCAG's gate is `≥ 4.5`, and axe computes to full precision, so the entire chain of documentation certified a failing pair. Nothing else in the palette sits this close to the line: the other two status tints clear at 4.61 and 4.76.
**Fix**: Added `--negative-text-on-tint` `#8F3D1F` (5.85 on `#FAE0D6`) beside `--brown-text-on-wash`, reusing the already-locked `--cta-destructive-bg-hover` value; `--status-rejected-fg` and the two report literals now take it. **Generalise**: a contrast figure quoted to 2 dp at exactly the gate is not evidence of passing — anything that rounds to 4.50 or 3.00 must be re-measured at full precision before it is written down, and written down as the unrounded number when it lands within 0.01 of the gate.
