## Policy design

Use the existing capability functions (no new ones unless specified):
- `is_super_admin()` — full access
- `is_admin()` — read/write
- `is_approved_user()` — read own row, read colleagues' public fields
- Self-row access via `auth.uid() = id`

## Migration SQL draft

```sql
-- W15.01 — users + people identity domain RLS
-- Replaces permissive SELECTs per Q-W14-d ledger

BEGIN;

-- users table
DROP POLICY IF EXISTS "<current permissive policyname>" ON public.users;

CREATE POLICY "users_select_self_or_colleague"
  ON public.users FOR SELECT TO authenticated
  USING (
    auth.uid() = id
    OR is_admin()
    OR (is_approved_user() AND <public-fields-only logic>)
  );

CREATE POLICY "users_update_self_or_admin"
  ON public.users FOR UPDATE TO authenticated
  USING (auth.uid() = id OR is_admin())
  WITH CHECK (auth.uid() = id OR is_admin());

-- workers table — similar pattern

-- people table — verify existing policies are capability-based (per matrix)

COMMIT;
```

## Follow-ups discovered elsewhere (to resolve before 🟢 close)

### W12.03b (2026-04-19) — `users_mgmt_write` UI/server asymmetry

W12.03b RBAC sweep tightened the UI role-change gate to `super_admin` only (new `change_user_role` capability). The server-side RLS policy `users_mgmt_write` on `public.users` still allows `management + super_admin` to `UPDATE`. Result: UI is now stricter than RLS. Not a security hole (UI direction, not server-opens-a-hole), but an enforcement asymmetry a future contributor could trip over if they assume UI = server. **Decision for W15.01 close**: either (a) tighten `users_mgmt_write` → `jwt_role() = 'super_admin'` to match the new UI capability, or (b) broaden the `change_user_role` capability to include `management` if the product intent is that both roles should manage users. Check `update_user()` RPC (no SECURITY DEFINER, pure SQL — authz is all at the RLS policy). Link: commit `18d2d80` + [../research/W12_03_SITES.md](../research/W12_03_SITES.md).
