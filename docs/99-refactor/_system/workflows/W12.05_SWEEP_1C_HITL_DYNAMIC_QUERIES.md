## Why this exists

During W12 Sweep 1 (2026-04-18), an exhaustive grep found 381 unbounded `.select()` calls. 153 were auto-fixed with `.limit(10000)` (mechanical). 29 are clearly list views needing PAGINATE (→ W12.02). **~218 fall into a grey zone** — they're inside dynamic query builders where:

- The bound depends on a runtime parameter (`limit` passed from UI)
- The query is built conditionally across many branches
- The `.select()` is chained off a shared `builder` variable that's extended elsewhere
- Marking LEGACY `.limit(10000)` could silently break a paginated flow that expected unbounded

These need one human-per-file verdict. Not a codemod target.

## Scope

Exact list is auto-generated when this card is executed, not pre-listed here (file moves across refactors will stale any static list). At run time:

```bash
# Find every .select() call and check if the same chain has a bound within 15 lines
grep -rn "\\.select(" src/ --include='*.ts' --include='*.tsx' \
  | while read -r hit; do
      file=$(echo "$hit" | cut -d: -f1)
      line=$(echo "$hit" | cut -d: -f2)
      # look at next 15 lines after the .select()
      has_bound=$(sed -n "${line},$((line+15))p" "$file" | grep -cE "\\.range|\\.limit|\\.single|\\.maybeSingle|head: true")
      if [ "$has_bound" -eq 0 ]; then
        echo "$file:$line — unbounded"
      fi
    done
# Subtract everything already covered by W12 (153 LEGACY) + W12.02 (29 PAGINATE) lists
```

Expected output: ~218 entries in dynamic-builder code paths.

## Per-file verdict workflow

For each file listed:
1. Open the file. Read 20 lines around the `.select()`
2. Answer 4 questions:
   - What table is being queried?
   - What's the expected row count? (rough estimate from live DB via MCP if unclear)
   - Does the calling UI paginate / scroll / display-all?
   - Is the query parameter-driven (accepts `limit` / `from` / `to` from caller)?
3. Pick a verdict:
   - **LEGACY-FIX**: single service call, expected result < 1000 rows → `.limit(10000)` safe
   - **PAGINATE**: list-view feeder → move to W12.02 scope instead
   - **PARAMETER-BOUNDED**: caller already controls bounds via runtime args → add `.limit(<default>)` + accept override
   - **ALREADY-OK**: the grep hit was a false alarm (bound is further down the chain)
   - **NEEDS_REDESIGN**: the call pattern itself is broken (e.g., fetch-all then filter client-side); ticket to W09 per-module migration
4. Apply the chosen fix
5. Type-check after each batch of ~10 files
