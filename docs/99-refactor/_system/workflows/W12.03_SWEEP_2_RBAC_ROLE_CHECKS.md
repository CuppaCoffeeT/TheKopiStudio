## Why this exists

Rule violation: hardcoded role checks bypass the dynamic module-permission system. The 8 violators will break when role-module mappings change (Admin Dashboard edits won't take effect on those pages until redeploy). Caught in REPO_AUDIT §3.

## The correct pattern

```tsx
// ❌ WRONG: hardcoded role check
const { user } = useAuth(['management', 'super_admin']);
if (!user || !['management', 'super_admin'].includes(user.role)) return null;

// ✅ CORRECT: module-based check
const MODULE_PATH = '/mymodule';
const { user, modules, loading } = useAuth();
const hasAccess = modules.some(m => m.path === MODULE_PATH);
```

## Migration pattern per file

1. Identify the module this page/component belongs to → find its path in `public.modules` via MCP
2. Replace the hardcoded role array with `modules.some(m => m.path === MODULE_PATH)`
3. Ensure `useEffect` redirect to `/dashboard` if no access (see [MODULE_SYSTEM.md §Complete Example](../../../01-system-architecture/MODULE_SYSTEM.md#module-access-control))
4. Playwright: log in as each role, verify access/denial matches the module permission matrix
