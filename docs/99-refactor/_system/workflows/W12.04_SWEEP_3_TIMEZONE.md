## Why this exists

Rule violation: raw `date-fns` uses the browser's local timezone. On a US-based dev laptop or a user traveling, dates shift by hours. Bugs this causes:
- Payroll "October" shows September entries when the browser is behind UTC
- Work-entry dates flip by 8 hours and look duplicate/missing
- Supervisor "today" filter returns yesterday's rows

177 offenders from REPO_AUDIT §6 (58% compliance gap — 75 compliant, 177 non-compliant).

## The correct pattern

```tsx
// ❌ WRONG: raw date-fns uses browser locale
import { format } from 'date-fns';
format(new Date(record.created_at), 'dd/MM/yyyy HH:mm');

// ✅ CORRECT: timezoneUtils forces SGT
import { formatDisplayDateTime } from '@/utils/timezoneUtils';
formatDisplayDateTime(record.created_at);
```

| Old call | Replacement |
|---|---|
| `format(d, 'dd/MM/yyyy')` | `formatDisplayDate(d)` |
| `format(d, 'dd/MM/yyyy HH:mm')` | `formatDisplayDateTime(d)` |
| `format(d, 'HH:mm')` | `formatDisplayTime(d)` |
| `parse(str, 'yyyy-MM-dd', new Date())` | `parseFromDateTimeLocal(str)` |
| `new Date()` for DB insert | `toUTCForDatabase(new Date())` |
| `startOfDay(d)` for "SGT today" | `getLocalDateString(d)` + comparison |

## Migration pattern

1. Codemod pass: auto-replace `format(x, 'dd/MM/yyyy HH:mm')` → `formatDisplayDateTime(x)` (and variants) using ast-grep
2. Manual review pass: cases where `date-fns` was used for non-display math (e.g. `addDays`, `differenceInMinutes`) — these stay as `date-fns` but through `timezoneUtils` re-export to keep the import boundary clean
3. Edge cases flagged for HITL: `startOfMonth`, `endOfMonth`, `isBefore` — each needs verification that the underlying date is in SGT before comparing
