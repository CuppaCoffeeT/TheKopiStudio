## 2026-04-27 — Don't search by `[test]`-bracketed strings in list-page seatbelt tests
**What happened**: WF-0099 cache-staleness filled the `quotations-search-input` with the seeded `project_name` `[test] WF-0099 original <runId>`. The `getPaginatedQuotations` OR-ilike returned 0 rows even though the row existed and direct SQL `ILIKE '%[test] WF-0099 ...%'` matched it. The page rendered "No matches for your filters."
**Root cause**: when an `or=(col.ilike.<value>,...)` PostgREST filter's value contains `[`/`]`/spaces, the live request observably returns zero rows — even though identical Postgres ILIKE works. Reproduced via the test failure, not the curl path (curl + anon hits RLS first).
**Fix**: drive the in-page search by the immutable numeric `runId` (14 digits, no special chars) — `runId` is embedded in both `quotation_number` (`Q${runId}/2099`) and `project_name`, so a single ilike still narrows to the seeded row. Keep the `[test] WF-<id>` prefix on `project_name` for cleanup matching only.

## 2026-04-27 — `page.goto()` remounts the SPA → ProtectedRoute renders just "Loading…" (8 chars body)
**What happened**: WF-9000 smoke test failed Gate 5 ("body is nearly empty (8 chars)") on ~9 routes (chromium-desktop) and ~16 routes (mobile-safari) after the 3s `networkidle` wait.
**Root cause**: every `page.goto(m.path)` is a full SPA reload. AuthContext re-hydrates session + modules on each navigation; until `loading=false`, ProtectedRoute renders only `<LoadingSpinner label="Loading…">` — 8 chars in `body.innerText`. `networkidle` 3s isn't enough headroom for the auth + modules query on cold pages, especially mobile-safari.
**Fix**: after `networkidle`, also `waitFor({ state: 'detached' })` on `getByText('Loading…', { exact: true })` with an 8s soft cap. Catch-and-continue so a genuinely-stuck page still trips Gate 5.

## 2026-04-27 — Quotation-create form wants ≥30s on first paint, not 15s
**What happened**: WF-0012 `waitForQuotationNumber` timed out at 15s on chromium-desktop + mobile-safari. The page rendered every section except the auto-populated `quotation_number` input.

## 2026-04-28 — Synthetic test Q-numbers (14-digit timestamps) overflow `get_next_quotation_number` INT cast
**What happened**: WF-0012 `waitForQuotationNumber` timed out at 30s and 60s; underlying `rpc/get_next_quotation_number` returned 400 with `value "20260428035426" is out of range for type integer` (SQLSTATE 22003). A single test residue row `Q77777777777777/2099` was enough to break ALL quotation creation portal-wide.
**Root cause**: WF-0013/WF-0099 seed quotations with `quotation_number = Q${14-digit-runId}/2099` to avoid colliding with real numbers. The original RPC scanned `Q%/%` and cast `SUBSTRING(quotation_number FROM '^Q(\d+)')` to `INTEGER` — INT4 max is ~2.1e9, but 14-digit runIds are ~2e13. Any leftover synthetic row poisons the next-number generator for everyone, including production.
**Fix**: migration `20260428_040029_harden_get_next_quotation_number_against_synthetic_qnumbers.sql` casts to `BIGINT` *and* filters `quotation_number NOT LIKE '%/2099'` so synthetic rows can't influence the calculation even semantically. The `2099` year suffix is the cross-suite convention for "this is a test seed". Tests can stay aggressive with their seeding scheme; the RPC is robust against it.

## 2026-04-28 — `fs.rmSync` / `rm -rf` can't beat QuickLook + SMB `.smbdelete*` holds; route deletes through Synology API
**What happened**: WF-0012 cleanup failed with `ENOTEMPTY` then `Resource busy: .smbdeleteAAA9ca8a4`. Even after `recursive: true`, sweeping `.DS_Store` / `._*`, retrying, and shelling out to POSIX `rm -rf`, the directory wouldn't disappear.
**Root cause**: macOS Finder's QuickLook daemon held a PDF preview mapped from the SMB share. macOS handles SMB deletes by renaming the file to `.smbdelete*` first, then unlinking when no opener remains — but QuickLook's mapping kept the file alive indefinitely. No amount of client-side rm could fix this.
**Fix**: added a `delete-folder` action to the `synology-nas` edge function (wraps the existing `deleteFolder()` method that calls `SYNO.FileStation.Delete` with `recursive=true`). `tests/runners/nasChecks.ts::hardDeleteNasFolder` is now async, calls the edge function as the authoritative path, polls Synology for confirmation via `waitUntilNasPathGone`, then best-effort `rm -rf` the local mount to clear the SMB dir-listing cache (failures here are tolerated — the directory is already gone server-side). Same playbook anywhere else SMB delete races kernel-held mappings: don't fight macOS, ask the server.

## 2026-05-20 — Explicit `waitForURL` timeout overrides the config's CI `navigationTimeout`
**What happened**: Seatbelt (W22) CI run #108 went red — 3 hard failures across both projects (`hr-applications-load`, `meetingprojects-load`, `dailyattendance-load`), all `page.waitForURL('**/dashboard', { timeout: 20_000 })` timing out after `LoginPage.signIn`. Failing tests varied run-to-run → environmental saturation, not a code bug.
**Root cause**: `playwright.config.ts` widens `navigationTimeout` to 30s on CI (so slow runners get headroom) — but a per-call `waitForURL(url, { timeout: 20_000 })` *overrides* the config value, capping the sign-in redirect at 20s. CI runners under the 2-project matrix routinely need 25-45s for the Supabase auth round-trip + post-login dashboard render.
**Fix**: bumped the explicit `waitForURL('**/dashboard')` timeout 20s→45s across all 171 callsites; bumped per-test `timeout` to 90s on CI so the longer sub-wait still leaves room for page load + axe. Local login is ~2-3s so the wider ceiling never bites off-CI.
**How to apply**: a per-call timeout always wins over `use.navigationTimeout` / `use.actionTimeout`. If a wait needs CI headroom, either omit the explicit timeout (inherit config) or set it ≥ the config's CI value.

## 2026-05-20 — Parallel CI workers collide on shared DB fixtures (company_name + matched_project FK)
**What happened**: W22 CI run #109 hard-failed 4 @p0 tests. (a) `customer-form-import` + `per-project-role` threw `duplicate key client_companies_company_name_key` in `beforeAll` — both the chromium-desktop and mobile-safari Playwright projects ran the spec and inserted an identical hardcoded `company_name`. (b) `import-dialog-override-match` tests 3 & 4 failed — the seeded `xero_invoices_cache` match row pointed `matched_project_id` at the shared `testInvoiceProject`; the parallel mobile-safari worker deleted/recreated that project mid-run, the FK went NULL (ON DELETE SET NULL), `hasExactMatch` flipped false, and the Override button never rendered (confirmed via the CI failure screenshot: "Match" badge but empty dropdown + no Override button).
**Root cause**: CI runs `workers: 2` — one per Playwright project — against the SAME prod database. Any fixture keyed on a hardcoded value (a fixed `company_name`, or a shared project id) is contended across the two workers. `companyUen` was already per-worker unique but `company_name` (the actual unique constraint) was not.
**Fix**: (a) embed the per-worker `companyUen` into `company_name` in both project-form-import specs (seed insert + the .xlsx form cell + the download-filename assertion). (b) `import-dialog-override-match` now creates its OWN isolated project + company in `beforeAll` instead of reusing `testInvoiceProject`, so no other worker can null the FK; also added search-isolation to `openImportDialog` (the Xero invoices table is paginated, the seed row isn't guaranteed on page 1) and surfaced the previously-silent seed upsert error.
**How to apply**: any spec that runs under both Playwright projects and writes to the DB must key every fixture on something per-worker unique (`workerInfo.project.name`). Never point a test's FK at a fixture another spec/worker mutates — own your fixtures or isolate them. Note `projects.project_number` is capped at 8 chars (`project_number_length`); `client_companies.uen` at 10 (`uen_max_length`).

## 2026-05-22 — Concurrent `playwright test` invocations race the shared prod fixture via globalTeardown
**What happened**: A pre-push @p0 run failed 8 mobile-safari payment-management tests — all FK violations on a missing `projects …010` / `quotations …020`. The same 8 specs passed on chromium-desktop in the same run; all 10 pass standalone. Locally `workers:1`, so chromium-desktop runs fully, then mobile-safari — the fixture vanished between the two phases.
**Root cause**: `globalSetup` seeds + `globalTeardown` hard-deletes ONE fixed-UUID fixture in the shared prod DB. They run once per `playwright test` invocation — but nothing guarded against TWO invocations overlapping (parallel agents, or a dev push during another run). The first invocation to finish runs its globalTeardown and deletes the fixture mid-suite for the still-running one. Distinct from the 2026-05-20 intra-run 2-worker contention — this is inter-INVOCATION.
**Fix**: `tests/fixtureLock.ts` — PID-file reference counting. `globalSetup` claims a lock; `globalTeardown` releases it and only performs the destructive delete when no other live run holds a lock. Fail-safe: a wrong "am I last" check errs toward NOT deleting (idempotent `globalSetup` re-seeds a lingering fixture next run).
**How to apply**: globalSetup/globalTeardown run per-invocation, not once-ever. Any teardown that mutates shared prod state must be guarded against concurrent invocations, not just concurrent workers.

## 2026-05-31 — Per-role test creds are split across TWO `.env.secrets` files; load both
**What happened**: The per-role harness (`testUsers.coordinator/supervisor/storeman`) needs `TEST_<ROLE>_EMAIL/PASSWORD`, but `testUsers.ts` only `config()`'d a SINGLE file — the volume `/Volumes/YourVolume/.env.secrets` when mounted, else the repo-local one. The volume file carries `AIGENT_*` + `SUPABASE_*` but NOT the `TEST_*` keys (those live only in the repo-local `.env.secrets`). So on a dev Mac with the volume mounted, every role password resolved empty.
**Root cause**: the keys are intentionally split — admin/service-role creds on the shared volume, role creds repo-local — and the old single-file `existsSync ? VOLUME : LOCAL` picked exactly one.
**Fix**: load BOTH files, each guarded by `existsSync` (`config({path: VOLUME})` then `config({path: LOCAL})`). dotenv does NOT override an already-set var and the two files hold disjoint keys, so loading order is safe. Per-role password guard is lazy (`requireTestUser(role)` throws only when that role is actually used), so an admin-only spec doesn't fail because a `TEST_STOREMAN_PASSWORD` is unset.
**How to apply**: when a fixture's secrets are split across files, `config()` each one (guarded) rather than picking one — dotenv's no-override semantics make disjoint multi-file loads order-independent. Per-role accounts are REAL plus-addressed Supabase logins (`aigent+<role>@`), not the client-only View-As preview (which can't exercise RLS).

## 2026-06-01 — Re-running a subset of failed specs: zsh doesn't word-split unquoted `$SPECS`
**What happened**: During a /git-full triage loop I collected failed spec paths into a var (`SPECS=$(cat failed-specs.txt | tr '\n' ' ')`) and ran `npx playwright test --config=playwright.parallel.config.ts $SPECS`. Playwright aborted with `Error: No tests found` even though each path matched fine individually via `--list`.
**Root cause**: the Bash tool's shell is **zsh** (user's login shell). Unlike bash, zsh does NOT field-split an unquoted scalar parameter on whitespace, so the whole newline/space-joined string was passed as ONE positional arg — a single regex that matched no file.
**Fix**: read into an array and expand with `"${SPECS[@]}"` — `SPECS=($(cat failed-specs.txt)); npx playwright test ... "${SPECS[@]}"`. The `$(...)` here DOES split on IFS when assigned to an array `(...)`, then `"${SPECS[@]}"` passes each path as its own arg.
**How to apply**: in any Bash-tool command that fans a list into a CLI, use a zsh array (`arr=($(...))` + `"${arr[@]}"`), never an unquoted scalar. Confirm a multi-path Playwright filter with `--list` (prints `Total: N tests in M files`) before launching a long background run.

## 2026-06-01 — OT-calculator grid is records-driven → empty on the 1st of the month (date-fragile specs)
**What happened**: `ot-calculator/{load-grid,create-modal-empty-cell,edit-modal-prefill}` all failed when the full suite ran on June 1. The grid renders 0 cells, `waitForSelector('[data-cell-w][data-cell-d]')` times out.
**Root cause**: `useOTCalculatorData` builds the worker list ONLY from `worker_ot` rows in the selected range (`if (!otRecords) return { workers: [] }`), and the page defaults to the current calendar month. On the 1st (before any OT is entered) there are zero rows → empty grid. NOT a code bug — identical on `main` (the hook was relocated byte-for-byte). `edit-modal-prefill` also hardcoded `2026-05-15` as the populated cell (already broken past May).
**Fix**: specs now `goto('/ot-calculator?from=<1st of last month>&to=<today>')` so the range always has data; `edit-modal-prefill` finds ANY populated OT cell (`[data-testid*="-ot-"]` filtered by `\d+\.\dh`); `create-modal-empty-cell` targets an OT sub-row showing `—` (a true entry-less day → CREATE) instead of any `—` cell (leave/missed days show `—` in non-OT sub-rows but HAVE an entry → opens EDIT, not create).
**How to apply**: a records-driven grid/list is empty at period boundaries. Date-pin such specs to a window known to hold data; never hardcode a calendar date; and disambiguate "empty cell" by the cell that actually drives the create-vs-edit branch.

## 2026-06-01 — StatusTabs collapses to a dropdown on overflow → mobile tab clicks hit a hidden element
**What happened**: 9 specs (plan-purchase-dashboard ×4, report-dashboard ×3, peoplemanagement ×2) failed ONLY on mobile-safari with "subtree intercepts pointer events" / 15s click timeouts on status tabs.
**Root cause**: `StatusTabs` (primitive) swaps the underline strip for a Popover dropdown when it overflows the container (narrow viewports). The strip stays mounted but `opacity-0 pointer-events-none` for overflow measurement and carries the SAME `data-testid` / `role="tab"`. So `getByTestId(id).click()` targets the hidden strip button, which the visible dropdown trigger intercepts. Desktop (no overflow) passes.
**Fix**: `tests/pom/statusTabs.ts` — `selectStatusTab` / `selectStatusTabByTestId` / `selectStatusTabByName`. It tries the direct click first (fast on desktop) and, on interception, opens the dropdown trigger (`button[aria-haspopup="dialog"]` under the tab's `role="tablist"` ancestor) and clicks the option inside the portaled `[data-radix-popper-content-wrapper]`, then waits for it to detach (the option duplicates the testid). Post-click `aria-selected`/`data-state` assertions still pass — the always-mounted strip reflects the active key.
**How to apply**: never pre-detect overflow synchronously — `useTabsOverflow` flips AFTER mount (mount effect + ResizeObserver), so a "is the trigger visible?" check races it. Attempt the desktop click with a short timeout and fall back to the dropdown on failure. Any spec clicking a StatusTabs tab MUST use this helper, else it fails on mobile-safari.

## 2026-06-01 — WebKit + Vite dev: "Importing a module script failed" on lazy route chunks
**What happened**: `claims-create-cross-project` (×5) + `agent/workflow-rail-load` failed ONLY on mobile-safari. The page renders fine, but a transient `pageerror: Importing a module script failed.` + React's error-boundary recovery log trip the specs' zero-console-errors assertions. (agent-rail's `/TooltipProvider/` filter matched because the error's componentStack mentions TooltipProvider.)
**Root cause**: WebKit under the Vite DEV server occasionally fails the FIRST dynamic `import()` of a route chunk; React Router's error boundary re-renders (a delayed retry) and recovers. CANNOT occur in prod (chunks are pre-bundled + hash-stable). An IMMEDIATE retry hits the same transient — only a DELAYED retry recovers.
**Fix**: `App.tsx` `lazyWithRetry` wraps every route `lazy()` with delayed retries (300ms, then 800ms) so the rejection never reaches the boundary (also hardens prod against post-deploy stale chunks). As a safety net, the two console-asserting specs ignore the dev-only fragments `'Importing a module script failed'` + `'React will try to recreate this component tree'` (meta-wrappers only — a REAL error still logs its own specific message, still caught; functional assertions still validate render).
**How to apply**: dynamic-import retries must be DELAYED, not immediate. A spec that asserts zero console errors on a lazy route must tolerate this WebKit-dev transient; do it by ignoring the specific dev-only fragments, never by dropping the assertion.

## 2026-06-01 — macOS has no `timeout(1)`; the Mini's launchd PATH lacks `node`
**What happened**: `comprehensive-run.sh` shelled `timeout 600 npx playwright …` and assumed `node`/`npx` on PATH. On both the dev laptop and the Mac Mini cron the script died: `timeout: command not found`, and under the Mini's launchd it also couldn't find `node` even though an interactive shell could.
**Root cause**: (a) macOS ships no GNU `timeout` — it's `gtimeout` only if coreutils is brew-installed. (b) launchd jobs start with a minimal PATH that does NOT include `/opt/homebrew/bin`, so the Homebrew node/npx (and gtimeout) are invisible even when present.
**Fix**: `comprehensive-run.sh` ships a portable `run_with_timeout` (try `gtimeout`, else `timeout`, else a background-process + sleep + `kill` fallback) and prepends `/opt/homebrew/bin` to `PATH` at the top of the script so brew binaries resolve under launchd.
**How to apply**: never assume `timeout`, `node`, or any brew binary on macOS cron/launchd. Provide a `gtimeout||timeout||background-kill` shim and `export PATH=/opt/homebrew/bin:$PATH` before invoking node tooling from a scheduled job.

## 2026-06-01 — cron-manager shell-job gotchas (stdout-swallow · /Volumes TCC · keychain flags · no --max-turns)
**What happened**: The comprehensive-run job, when scheduled via the Mini's cron-manager, repeatedly misbehaved: `log()` output vanished, env loading from `/Volumes` flaked, and `claude -p` returned "Not logged in" despite a working interactive login.
**Root cause**: four distinct shell-job traps. (1) The job captures the script's stdout (`$(...)`); a `log()` that `echo`s to stdout gets swallowed into the captured value instead of appearing in the job log. (2) `cp`/`source` against `/Volumes/YourVolume/.env.secrets` is TCC-flaky under launchd (the mount's privacy ACL intermittently denies the daemon). (3) `claude --no-session-persistence` and `claude --bare` both disable keychain access → headless `claude -p` reports "Not logged in". (4) `--max-turns` does not exist in `claude` v2.1.126, so passing it aborts the invocation.
**Fix**: `log()` writes to **stderr** (`>&2`) so it never pollutes captured stdout; env loads from a repo-local `.env.secrets` or, when reading the volume, via `dd if=/Volumes/… ` (TCC-stable where `cp`/`source` aren't); never pass `--no-session-persistence`/`--bare` (let the default session keep keychain); bound agent loops in the shell (retry counter) rather than the non-existent `--max-turns`.
**How to apply**: for any cron-manager shell job — `log()` to stderr, prefer repo-local secrets or `dd`-from-volume over `cp`/`source`, keep the default `claude` session for keychain, and never reach for `--max-turns` on v2.1.x.

## 2026-06-01 — fixtureLock.ts is a per-HOST PID file → cross-machine clone races the shared prod fixture
**What happened**: When the Mac Mini ran the comprehensive clone of the suite while the laptop ran a full-suite pass, both invocations' `globalTeardown` deleted the shared prod fixture out from under the other — exactly the inter-invocation race `fixtureLock.ts` was meant to prevent, but across two machines.
**Root cause**: `fixtureLock.ts` guards via a PID file in `os.tmpdir()` and probes liveness with `process.kill(pid, 0)`. Both the path and the probe are **host-local** — a PID on the Mini means nothing on the laptop, and neither host can see the other's lock file. The lock only serialises invocations on the SAME machine.
**Fix (mitigation)**: schedule the comprehensive run in a nightly window when the dev (laptop) is asleep, and gate the whole comprehensive run behind `comprehensive-run.sh`'s single-run `mkdir` lock (mkdir is atomic, but still host-local — it only prevents a second comprehensive run on the same Mini). The operational rule is the real fix: never run the comprehensive suite concurrently with a laptop full-suite run.
**How to apply**: a tmpdir PID file does NOT lock across machines. Any teardown that mutates shared prod state from >1 host needs either a DB-backed/NAS-backed lock or an operational non-overlap window. Until a cross-host lock exists, treat "Mini comprehensive run" and "laptop full-suite run" as mutually exclusive.

## 2026-06-01 — `dd` from /Volumes ALSO fails under the cron-manager context → a complete LOCAL `.env.secrets` is REQUIRED
**What happened**: The first real `/run` of `appbase-nightly-e2e` failed at +3s, exit 2: "no local .env.secrets and dd from /Volumes/YourVolume/.env.secrets failed" — even though the mount preflight (`[ -d /Volumes/JLQI ]`) passed and an interactive SSH session could `grep` that file fine.

Compounding: the NAS `.env.secrets` lacks the per-role `TEST_*` creds (those live only in the laptop's repo-local copy), so even a working `dd` wouldn't satisfy the 4-role auth setup.

The script prefers a local file, so the `dd` fallback never runs.
**Supersedes**: 2026-06-01 — cron-manager shell-job gotchas (the "`dd`-from-volume is TCC-stable" claim — it is NOT in the cron-manager process context).
**How to apply**: for any launchd/cron job needing secrets on a TCC-protected volume, copy them to a local file during provisioning from a context that HAS access (interactive SSH); never rely on the scheduled job reading `/Volumes` contents. `[ -d ]` passing ≠ readable file contents.

## 2026-06-02 — Full parallel suite's "~50 failures" were shared-fixture seed contention, not bugs
**What happened**: The full `playwright.parallel.config.ts` suite reported 38–54 hard failures at workers=2/3/6 (projectdetail writes, quotation, payment-management, worker-ot, form-import, templatefile). A workers=1 serial run of the same specs was clean (only genuine real bugs).
**Root cause**: those specs target FIXED seed entities (e.g. project `7f0a6480`/7709 + a fixed `quotation_line_item`, a single shared `TEST_WORKER_ID`, fixed fixture PCs) and clean up with BROAD deletes (`delete WHERE project_id = TEST_PROJECT_ID`). The SAME spec runs on both `chromium-desktop` AND `mobile-safari`; at workers≥2 those two instances (or two different specs on the same project) race — one's broad cleanup wipes the other's just-inserted row → `Received: null` / count 0 / "Cannot coerce result to single JSON object". `fullyParallel:false` only serialises WITHIN a file, not across the desktop/mobile projects.
**Fix (interim)**: run the full suite at `E2E_WORKERS=1` — the only contention-free config today. The real fix (future work) is per-spec seed isolation: unique data per (spec × project) + cleanup scoped to only the rows that spec created, not the whole project.
**How to apply**: a parallel E2E failure that returns null/0/"coerce" on a DB-write spec is almost always seed contention, not a product bug — confirm by re-running that spec at workers=1 before "fixing" the product. Don't widen worker count to chase speed until seed isolation lands.

## 2026-06-02 — `vite preview` (prod build) beats the dev server for full-suite load stability — gate Vercel Analytics
**What happened**: At equal workers, the Vite DEV server produced far more failures than a pre-built `vite preview` server (dev 6w = 54 vs preview 6w = 38). Dev-only failure modes: route chunks compile lazily in one process so N workers back up the compile queue (routes return near-empty bodies / bounce to /login, slow loads race spec interactions); WebKit/mobile-safari hits the documented lazy-import transient; and over a long workers=1 run (~80 min) the dev server DEGRADES (late mobile specs time out at ~46s).
**Root cause**: dev = on-demand compile + HMR + single long-lived process. Preview serves pre-bundled, hash-stable chunks — no cold-compile, no lazy-import transient, no degradation. Caveat: a prod build runs `@vercel/analytics` in production mode, which loads `/_vercel/insights/script.js`; that endpoint only exists on Vercel's edge, so on localhost/`vite preview`/CI it 404s → pollutes the console → trips console-clean specs (progress-claim-detail).
**Fix**: gate `<Analytics/>` in `main.tsx` to `window.location.hostname === 'your-app.example.com'` only. To run the suite on preview: `npm run build` → `npm run preview -- --port 8080 --strictPort` (background) → run playwright (base `reuseExistingServer:true` reuses it). NOTE `_tools/snapshot-modules.spec.ts` hardcodes `localhost:8080`, so preview MUST be on 8080.
**How to apply**: for a reliable FULL-suite run, prefer a pre-built preview server on :8080 over `npm run dev`. Don't load third-party analytics/telemetry on non-prod hosts — it 404s and breaks console-clean assertions.

## 2026-06-02 — Running many full suites back-to-back exhausts the Supabase connection pool (522 / timeouts)
**What happened**: After ~7 full-suite runs + serial probes against PROD Supabase in a few hours, global-setup began failing with Cloudflare `522 Connection timed out` and direct queries with "Connection terminated due to connection timeout". `get_project` still read `ACTIVE_HEALTHY` and PostgREST root returned 401, but any REAL query (service-role SELECT) timed out at 15s.
**Root cause**: the suite (global-setup/teardown + per-spec service-role DB clients + per-worker app sessions) opens many Postgres connections; a rapid run cadence (especially killing runs mid-flight) outpaces connection reaping → pool exhaustion at the data layer. Control-plane health ≠ data-plane health; PostgREST root 401 ≠ DB reachable (it doesn't touch Postgres).
**Fix**: stop all load and wait for the pool to drain (poll a real service-role REST query for HTTP 200, ~60–90s interval, not aggressively). Re-run at workers=1 (lightest connection footprint).
**How to apply**: don't fire full E2E suites back-to-back against prod. Probe health with a query that actually hits Postgres (`/rest/v1/<table>?select=id&limit=1`), not the PostgREST root. If a run aborts at global-setup with 522/timeout, it's infra, not the code under test.

## 2026-07-14 — reuseExistingServer silently reused ANOTHER project's dev server
**What happened**: Playwright runs with `reuseExistingServer: true` attached to a dev server on 8080/8081 belonging to a DIFFERENT project (JLCMS trench-trace-portal holds both ports), so specs ran against the wrong app and failed confusingly.
**Root cause**: `reuseExistingServer` only checks that the port answers — it cannot tell whose app is listening; both ports were already taken by another repo's servers.

## 2026-07-27 — The CI e2e matrix is two HOSTS sharing one live book: the tmpdir mutex cannot see across them
**What happened**: First CI run to get far enough to actually execute specs (earlier runs died on `npm ci`, then missing env, then ENOENT auth files) came back 45 passed / 2 failed. `reports/portfolio-convert.spec` read "Expected 3, Received 2" then "Expected 1, Received 2" on retry; `crm/dashboard.spec` timed out in `ClientsPage.waitForDetail` mid residue-sweep. Both specs **held** the advisor-book lock when they broke.
**Root cause**: the matrix `project: [chromium-desktop, mobile-safari]` runs as two GitHub jobs on two separate runners, both writing the same live Supabase advisor book with the same account. `tests/fixtures/advisorBookLock.ts` is a `mkdirSync` on `os.tmpdir()` + `process.kill(pid, 0)` — both host-local, so each leg's lock is invisible to its peer. Holding the lock and still seeing corrupt baselines is the signature: the writer was on another machine. This is the 2026-06-01 fixtureLock cross-host lesson recurring in a new place.
**Smoking gun**: re-running the two specs locally to reproduce, the sweep died on client `c37b12c4-…` rendering `NoResultsState` on `/clients/<id>`. That row was `E2E-Rpt-mobile-safari-r1-1785147781024` — created at 10:23:05Z by the mobile-safari CI runner still in flight, and soft-deleted between the local run's list read and its detail navigation. The peer job **names itself in the fixture**, so the evidence was in the row all along. Re-run once CI finished, uncontended: 10/10 passed in 45s (vs 1.8m and a failure while contended), advisor book verified empty in SQL. No app regression — the redesign is not implicated.
**Fix**: `max-parallel: 1` on the e2e matrix in `.github/workflows/seatbelt.yml` — an operational non-overlap window, which that lesson names as the remedy until a DB-backed cross-host lock exists. Also reverted the CI step to the base `playwright.config.ts` (dropped `--config=playwright.parallel.config.ts`).
**Postscript (same day)**: with the matrix serialised, both legs passed — and the run STILL reported failure, because the `sync-ledger` job then crashed with `FileNotFoundError: docs/99-refactor/_system/ledgers/WORKFLOW_LEDGER.md`. That file has never existed here (`git log --all` on the path: empty); the job was AppBase scaffolding. It hid for months behind `if: success()` — it could only run once both earlier jobs were green, which had never happened on this repo. **The first truly green run was reported red, caused by passing.** Job removed; workflow `permissions` dropped `contents: write` → `read` since nothing pushes back now. Generalisation: a CI step gated `if: success()` is untested until the day everything else passes, so it fails at the worst possible moment — audit success-gated steps by running them deliberately, not by waiting.
**How to apply**: three things, all bitten this week. (0) **Do not run the CRM/reports suite locally while a CI run is live** — your laptop is a third writer against the same prod book and the tmpdir lock cannot see the runners either. Check `gh run list --limit 1` first; a red local run during CI proves nothing. (1) Before trusting ANY mutex under a CI matrix, ask whether the matrix legs share a host — a matrix is not a worker pool, it is N machines, and every `os.tmpdir()` lock in this repo silently degrades to a no-op across them. (2) Don't point CI at `playwright.parallel.config.ts`: its own header says local-only, and it overrides `workers` to 10 and `retries` to 1, so CI went from 2 browsers to 10 on a 2-vCPU runner — that oversubscription is the likelier cause of the 30s `waitForDetail` timeout than any app change. It selects the identical 45 specs (`testIgnore: '**/auth/**'` matches nothing — `tests/workflows/auth/` does not exist), so there was never coverage to gain. Verify config swaps with `npx playwright test --grep @p0 --project=<p> --list` and compare the totals; `--grep` does NOT filter out `setup`, because Playwright exempts dependency projects.

## 2026-08-13 — Seeding a test account means seeding THREE role surfaces, not one
**What happened**: Writing `tests/setup/seed-auth-users.mjs` for the ephemeral CI database, the obvious implementation — `auth.admin.createUser()` then `UPDATE public.users SET role, is_approved, is_active` — was drafted, and it is what the handoff doc specified. It would have produced three accounts that sign in perfectly and then behave as if they had no permissions at all: manager's `/clients` empty, `results-manager` and `results-superadmin` asserting against nothing, every capability check failing closed. Caught by reading the dumped schema before the first CI run, not by a red run.
**Root cause**: the role is denormalised across three places and each one backs a different mechanism. (1) `has_capability()` and `is_super_admin()` read `auth.jwt()->'app_metadata'->>'role'` — the JWT, **not** `public.users` — so `view_all_clients` / `view_all_results` / `manage_accounts` are decided entirely by what gotrue stamped into the token. (2) `public.users.role` drives module grants via `role_modules`, and `is_approved`/`is_active` gate `/dashboard` through `is_approved_user()`. (3) `public.profiles.role` is what `get_my_role()` returns, and the "Managers read all results/profiles" policies are written against `get_my_role() = 'manager'` — its CHECK allows only `advisor|manager`, so **super_admin has to be stored there as `manager`**. In prod nothing keeps these in sync automatically; `supabase/functions/role-sync/index.ts` writes all three by hand, which is exactly why it exists.
**Fix**: the seed script sets all three per user — `app_metadata: { role }` on create, then `public.users` (role + approved + active), then `public.profiles` with the super_admin→manager mapping copied from role-sync v2. It then verifies: re-reads the users row, asserts the role resolves to ≥1 granted module, and performs a real `signInWithPassword` through the **anon** key. Related: `[edge_runtime]` had to stay enabled in `config.toml` — `manage-accounts.spec.ts` drives the role round-trip through `/functions/v1/role-sync` and restores the advisor role in `afterAll` by POSTing it directly, so disabling the runtime to save an image pull 404s both halves.
**How to apply**: when provisioning a user outside the app's own signup path, grep the RLS helpers for where they actually read the role before assuming `public.users` is authoritative — `auth.jwt()->'app_metadata'` does not update when you UPDATE a table. And when a fixture-seeding script can fail silently into "logged in but sees nothing", make it prove the end state itself (sign in, count grants) rather than leaving it for the specs to discover thirty timeouts later.

## 2026-08-13 — Correction: the super_admin's profiles.role is 'advisor', and "Bee zhen" needs a fourth account
**What happened**: The entry above got the third role surface wrong. It said super_admin maps to `profiles.role = 'manager'`, copying role-sync v2's mapping. ## 2026-08-13 — Making the database fast turned a latent axe race into six red specs
**What happened**: Moving CI to an ephemeral local Supabase turned six a11y specs red at once, all `color-contrast`, all `serious`, all on ordinary `--fg-dim` text that is perfectly legible. Nothing about the theme had changed.
**Root cause**: axe computes contrast on the alpha-blended colours it sees AT SCAN TIME, and every surface in this app carries `motion-rise` entrance animations (`src/index.css` — `rise-in`, staggered 70/140/210/280ms, 600ms for heroes). The scans were landing mid-fade. Against the remote Supabase, latency on the in-flight auth/modules queries reliably pushed each scan past the animation window, so the race was invisible for months; a local DB answering in single-digit milliseconds removed that accidental delay. The tells were both in the output: the reported node count varied 4 → 11 across retries of ONE identical test (a real contrast bug reports the same nodes every time), and one offending target was literally `.motion-rise-3`.
**Fix**: `tests/runners/a11yChecks.ts` — one `expectWcag2aaClean` that settles the page's finite animations before injecting axe. The suite already HAD `settleAnimations` and a comment explaining exactly this failure mode, but it had been written for modals and only the modal scans called it; the helper had also been copy-pasted byte-identically into three spec files, so there was no single place to fix. This also fixed `profiler/load-a11y:69`, which fails on `main` against prod for the same reason — that page issues no queries, so it renders instantly in BOTH environments, which is precisely why it was the one a11y failure common to both.
**How to apply**: an assertion that passes only because the environment is slow is not passing. When a suite moves to faster infrastructure, expect latent ordering races to surface as a cluster of unrelated-looking failures, and read the *variance* in a failure (differing node counts, differing selectors) as the signature — a genuine defect is stable. And when a helper exists to prevent a class of bug, check it is called everywhere that class can occur, not just where it was first found; three copies of one function is three places to forget.

## 2026-08-13 — Consolidating four copies of a helper missed the fifth, and it turned main red
**What happened**: After folding `expectWcag2aaClean` out of the three `*a11y*.spec.ts` files (and later a fourth, `auth-public.spec.ts`) into `tests/runners/a11yChecks.ts`, four consecutive CI runs on the branch went green — including two on the exact commit that was merged. The push to `main` then went red on one mobile-safari test: `portfolio-convert.spec.ts` scanning the populated `/crm-reports`, one `serious` colour-contrast node on the print CTA.
**Root cause**: a **fifth** private copy of the helper, in `portfolio-convert.spec.ts`. It skipped the animation settle, so that scan still raced the entrance fade. I found the first four by grepping for the file-naming pattern `*a11y*` and by reading the specs that had failed — both searches that select on where the bug had already *shown up*, not on where it could exist. This spec scans a11y but says nothing about a11y in its name, so it fell outside both. It was also intermittent (green on 4 runs, red on the 5th), which is exactly what a race looks like and is why the branch runs did not catch it.
**Fix**: point it at the shared runner, and make a sixth copy impossible rather than merely unlikely — an ESLint `no-restricted-imports` rule banning `axe-playwright` anywhere under `tests/**` except the runner itself. Verified it errors by probing with a throwaway importer before removing it.
**How to apply**: when consolidating duplicated logic, enumerate by what the code IMPORTS, not by filename or by which copies have misbehaved — `grep -rn "from 'the-package'"` finds every call site; a filename convention finds the ones you already knew about. And when the consolidation exists to make a wait unskippable, land the lint rule in the same change: a shared helper that callers can still bypass has not removed the failure mode, it has only made it rarer, and rarer means it surfaces after the merge instead of before it. Corollary, learned the hard way here: a green branch run is not proof for an intermittent failure — four were not enough.
